## 问题3：抽象解决了什么问题？

### 情景模拟：3个程序 × 3种CPU = 多少份代码？

**不抽象的情况：**

假设你要写3个程序（A、B、C），要在3种CPU上运行（x86、RISC-V、MIPS）：

```
程序A:
  - A-x86.c
  - A-riscv.c
  - A-mips.c

程序B:
  - B-x86.c
  - B-riscv.c
  - B-mips.c

程序C:
  - C-x86.c
  - C-riscv.c
  - C-mips.c
```

**需要维护：3 × 3 = 9份代码！**

**有抽象（AM）的情况：**

```
程序A: A.c (调用AM API)
程序B: B.c (调用AM API)
程序C: C.c (调用AM API)

AM实现:
  - am/src/x86/nemu/    (x86的实现)
  - am/src/riscv/nemu/  (RISC-V的实现)
  - am/src/mips/nemu/   (MIPS的实现)
```

**只需要维护：3 + 3 = 6份代码！**

而且，如果增加新程序，只需要写1份；增加新架构，只需要实现AM。

## 代码探索：不同ISA的 `halt()` 实现

查看 `nemu.h` 中不同ISA的实现：

```c
// abstract-machine/am/src/platform/nemu/include/nemu.h

#if defined(__ISA_X86__)
# define nemu_trap(code) asm volatile ("int3" : :"a"(code))
#elif defined(__ISA_MIPS32__)
# define nemu_trap(code) asm volatile ("move $v0, %0; sdbbp" : :"r"(code))
#elif defined(__riscv)
# define nemu_trap(code) asm volatile("mv a0, %0; ebreak" : :"r"(code))
#elif defined(__ISA_LOONGARCH32R__)
# define nemu_trap(code) asm volatile("move $a0, %0; break 0" : :"r"(code))
#endif
```

### 相同点：
1. 都调用 `nemu_trap(code)`
2. 都通过内联汇编实现
3. 都把 `code` 传入寄存器
4. 都触发特殊指令让NEMU识别

### 不同点：

| ISA | 寄存器 | 指令 | 说明 |
|-----|--------|------|------|
| **x86** | `a` (eax) | `int3` | x86的断点中断指令 |
| **MIPS32** | `$v0` | `sdbbp` | MIPS的调试断点指令 |
| **RISC-V** | `a0` | `ebreak` | RISC-V的环境断点指令 |
| **LoongArch** | `$a0` | `break 0` | LoongArch的断点指令 |

**为什么不同？**
- 不同ISA的寄存器命名不同（eax vs a0 vs $v0）
- 不同ISA的断点指令不同（int3 vs ebreak vs sdbbp）
- 不同ISA的调用约定不同（参数传递方式）

## 思考：为什么 `memcpy()` 不需要分架构实现？

### `memcpy()` 的实现（架构无关）

```c
// abstract-machine/klib/src/string.c
void *memcpy(void *out, const void *in, size_t n) {
  // 可以用纯C语言实现，不依赖特定ISA
  char *dst = (char *)out;
  const char *src = (const char *)in;
  for (size_t i = 0; i < n; i++) {
    dst[i] = src[i];
  }
  return out;
}
```

**为什么架构无关？**
1. 只使用C语言基本操作（指针、循环、赋值）
2. 不依赖特定ISA指令
3. 不依赖特定寄存器
4. 编译器会生成对应架构的代码

### `halt()` 的实现（架构相关）

```c
// 必须用内联汇编，因为：
// 1. 需要调用特定ISA的指令（int3/ebreak/sdbbp）
// 2. 需要按照特定ISA的调用约定传递参数
// 3. 需要访问特定ISA的寄存器
```

**为什么架构相关？**
1. 需要特定ISA的指令（如 `ebreak`）
2. 需要按ISA的调用约定传参（寄存器选择）
3. 需要直接操作硬件（触发NEMU的特殊处理）

| 方面 | 不抽象 | 有抽象（AM） |

| **开发效率** | 低（重复工作） | 高（复用实现） |

## 更深层的理解：架构相关 vs 架构无关

### 架构相关的函数（需要分ISA实现）

```c
// 这些函数必须分架构实现，因为：
halt()      // 需要ISA特定的指令
putch()     // 需要ISA特定的I/O方式
cte_init()  // 需要ISA特定的中断处理
vme_init()  // 需要ISA特定的内存管理
```

**原因：**
- 直接操作硬件
- 使用ISA特定指令
- 遵循ISA特定约定

### 架构无关的函数（只需一份实现）

```c
// 这些函数可以统一实现，因为：
memcpy()    // 纯C语言，编译器处理
strlen()    // 纯C语言，编译器处理
malloc()    // 使用AM的heap API，不直接操作硬件
printf()    // 使用AM的putch() API
```

**原因：**
- 只使用C语言基本操作
- 通过AM API间接访问硬件
- 编译器负责生成对应架构的代码

## 实际例子：看看AM如何工作

### 程序的视角（统一接口）：

```c
// 你的程序（架构无关）
int main() {
  halt(0);  // 调用AM API，不关心底层实现
  return 0;
}
```

### AM的实现（架构相关）：

```c
// x86的实现
void halt(int code) {
  asm volatile ("int3" : :"a"(code));  // x86方式
}

// RISC-V的实现
void halt(int code) {
  asm volatile("mv a0, %0; ebreak" : :"r"(code));  // RISC-V方式
}

// MIPS的实现
void halt(int code) {
  asm volatile ("move $v0, %0; sdbbp" : :"r"(code));  // MIPS方式
}
```

**关键点：**
- 程序只调用 `halt(0)`，不关心底层
- AM负责把 `halt(0)` 转换成对应ISA的实现
- 不同架构的实现不同，但接口相同

## 总结：抽象解决了什么问题？

### 1. **代码复用**
- 不抽象：每个程序要为每个架构写一份
- 有抽象：程序写一次，AM为每个架构实现一次

### 2. **维护成本**
- 不抽象：修改需要改n×m处
- 有抽象：修改集中在AM实现

### 3. **可移植性**
- 不抽象：程序绑定特定架构
- 有抽象：程序可以在任何实现了AM的架构上运行

### 4. **开发效率**
- 不抽象：重复实现相同逻辑
- 有抽象：专注于业务逻辑，底层由AM处理

## 关键洞察

**为什么 `memcpy()` 不需要分架构？**
- 它是纯C语言实现，编译器会生成对应架构的代码
- 不直接操作硬件，不依赖ISA特定指令

**为什么 `halt()` 需要分架构？**
- 需要调用ISA特定的指令（`int3`/`ebreak`/`sdbbp`）
- 需要按照ISA的调用约定传递参数
- 直接与硬件交互

**抽象的核心思想：**
- 把架构相关的部分（如 `halt()`）封装在AM中
- 程序只调用统一的API，不关心底层实现
- 这样程序就可以在多个架构上运行，而无需修改

这就是抽象的价值：让程序与架构解耦，提高可维护性和可移植性。
