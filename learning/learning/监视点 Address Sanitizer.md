## Address Sanitizer 的基本原理

### 1. 它是工具，不是框架代码实现的

Address Sanitizer（ASan）是编译器（GCC/Clang）提供的工具，不是框架代码实现的。

在 NEMU 中的使用方式：

```49:49:nemu/Makefile
CFLAGS_BUILD += $(if $(CONFIG_CC_ASAN),-fsanitize=address,)
```

这只是添加编译选项，编译器会自动处理。

### 2. 核心原理：影子内存（Shadow Memory）

#### 基本思想

ASan 使用影子内存机制：为应用程序内存的每 8 字节分配 1 字节的影子内存，记录这 8 字节的可访问状态。

```
应用程序内存         影子内存
┌─────────────┐      ┌─────────┐
│ 0x1000-0x1007 │ ──→ │ 0x2000 │  (1字节，记录8字节的状态)
│ 0x1008-0x100F │ ──→ │ 0x2001 │
│ 0x1010-0x1017 │ ──→ │ 0x2002 │
│     ...      │      │  ...   │
└─────────────┘      └─────────┘
```

#### 影子内存的值含义

| 影子内存值 | 含义 | 示例 |
|-----------|------|------|
| **0** | 对应的 8 字节全部可访问 | 正常分配的内存 |
| **1-7** | 前 k 字节可访问，后续不可访问 | 数组边界、对象边界 |
| **负数** | 该区域不可访问 | Redzone、已释放内存 |

### 3. 实现机制：编译器插桩（Instrumentation）

#### 编译时自动插入检查代码

原始代码：
```c
int arr[10];
arr[5] = 42;  // 正常访问
arr[15] = 99; // 越界访问！
```

启用 ASan 后，编译器自动转换为：
```c
int arr[10];
// 编译器自动插入的检查代码
__asan_check_store(&arr[5], 4);  // 检查写入4字节是否合法
arr[5] = 42;

__asan_check_store(&arr[15], 4); // 检查写入4字节是否合法
// 如果 arr[15] 在影子内存中标记为不可访问，程序会立即报错
arr[15] = 99;
```

#### 内存分配时的处理

原始代码：
```c
void *p = malloc(100);
```

启用 ASan 后，实际调用：
```c
// ASan 拦截 malloc，分配更多内存
void *p = __asan_malloc(100);
// 实际分配：100字节数据 + 左右各32字节的redzone = 164字节
// 并在影子内存中标记可访问区域
```

内存布局：
```
┌─────────────┬──────────────┬─────────────┐
│ Redzone(32) │  Data(100)   │ Redzone(32) │
│ 不可访问    │   可访问      │  不可访问   │
└─────────────┴──────────────┴─────────────┘
```

### 4. 如何检测不同类型的错误？

#### 检测缓冲区溢出

```c
int arr[10];
arr[10] = 99;  // 越界访问
```

检测过程：
1. 编译器插入检查：`__asan_check_store(&arr[10], 4)`
2. 计算影子内存地址：`shadow_addr = (addr >> 3) + offset`
3. 读取影子内存值：如果为负数或超出范围，说明是 redzone
4. 报告错误：立即终止程序并输出错误信息

#### 检测 Use-After-Free

```c
int *p = malloc(100);
free(p);
*p = 42;  // 使用已释放的内存
```

检测过程：
1. `free(p)` 时，ASan 将对应内存标记为不可访问（在影子内存中标记）
2. 访问 `*p` 时，检查影子内存发现该区域不可访问
3. 报告错误：`ERROR: AddressSanitizer: heap-use-after-free`

#### 检测内存泄漏

ASan 包含 LeakSanitizer（LSan）组件：
- 程序退出时扫描所有分配的内存
- 如果发现未释放的内存，报告泄漏

### 6. 工作原理总结

```
┌─────────────────────────────────────────┐
│  1. 编译时（Compiler）                   │
│     - 解析源代码                        │
│     - 在内存访问前插入检查代码          │
│     - 替换 malloc/free 为 ASan 版本     │
└─────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────┐
│  2. 链接时（Linker）                    │
│     - 链接 ASan 运行时库                │
│     - 设置影子内存映射                  │
└─────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────┐
│  3. 运行时（Runtime）                    │
│     - 分配内存时更新影子内存            │
│     - 每次内存访问检查影子内存          │
│     - 发现错误立即报告                  │
└─────────────────────────────────────────┘
```

### 7. 性能开销

为什么会有性能开销？
- 每次内存访问都要检查影子内存（额外 1-2 次内存访问）
- 内存分配时设置影子内存
- 内存布局改变（redzone 等）

典型开销：
- CPU 开销：约 2-3 倍
- 内存开销：约 2-3 倍

### 8. 与其他工具对比

| 特性 | Address Sanitizer | Valgrind | 手动 assert |
|------|------------------|----------|-------------|
| **实现方式** | 编译器插桩 | 动态二进制插桩 | 手动添加代码 |
| **性能开销** | 2-3倍 | 10-50倍 | 几乎无开销 |
| **检测时机** | 运行时 | 运行时 | 运行时 |
| **使用方式** | 编译选项 | 外部工具 | 代码中插入 |
| **检测能力** | 全面 | 全面 | 有限 |

### 9. 实际示例

假设在监视点代码中有 bug：

```c
// watchpoint.c
void new_wp(char *expr_str) {
  WP *wp = free_;
  
  // Bug: 没有检查 free_ 是否为 NULL
  free_ = free_->next;  // 如果 free_ 是 NULL，这里会崩溃
}
```

启用 ASan 后运行：
```
==12345==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000
    #0 0x401234 in new_wp watchpoint.c:55
    #1 0x401567 in cmd_w sdb.c:143
    #2 0x401890 in sdb_mainloop sdb.c:240

Address 0x0 is not stack'd, malloc'd or (recently) free'd
```

ASan 会指出：
- 错误类型：段错误（空指针解引用）
- 错误位置：`watchpoint.c:55`
- 调用栈：完整的函数调用链

## 总结

Address Sanitizer 是什么？
- 编译器提供的工具，不是框架代码实现的
- 通过编译器插桩自动插入检查代码
- 使用影子内存机制跟踪内存状态

基本原理：
1. 影子内存：每 8 字节应用内存对应 1 字节影子内存
2. 编译器插桩：在内存访问前自动插入检查
3. 运行时检测：每次访问都检查影子内存状态
4. 立即报告：发现错误立即终止并输出详细信息

在 NEMU 中的使用：
- 只需在 menuconfig 中启用选项
- 编译器自动处理所有细节
- 无需修改任何源代码
- 重新编译即可生效

这是编译器提供的工具，不是框架代码实现的。你只需要启用编译选项，编译器会自动完成所有工作。
