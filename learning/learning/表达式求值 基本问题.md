

## 问题1：为什么不能直接用 `eval()` 函数？

### 简单回答
因为你的程序（NEMU调试器）需要计算的是包含寄存器和内存地址的表达式，而不仅仅是纯数字。

### 具体原因

想象你在调试一个程序，想知道某个内存地址的值：

```
你想要：p $eax + 4 * ($ebx - 1)
```

这里的 `$eax` 和 `$ebx` 不是数字，而是：
- `$eax` = 寄存器eax的当前值（比如运行时是 0x1234）
- `$ebx` = 寄存器ebx的当前值（比如运行时是 0x5678）

Python的 `eval()` 或其他语言的 `eval()` 不认识 `$eax` 这种符号，它们只能计算纯数字表达式。

### 类比：翻译问题

```
Python的eval()：只能理解 "5 + 4 * 3"
你的调试器：需要理解 "$eax + 4 * ($ebx - 1)"
```

就像中文翻译器只能理解中文，但你需要一个能理解"中文+英文+特殊符号"的翻译器。

### 代码证据

看代码中的使用场景：

```c
// 在 sdb.c 中
static int cmd_p(char *args) {
  bool success = false;
  word_t result = expr(args, &success);  // 这里的args可能是 "$eax + 4"
  ...
}
```

`expr()` 函数需要：
1. 识别 `$eax` 这样的寄存器名
2. 从NEMU中读取该寄存器的值
3. 再进行计算

标准的 `eval()` 做不到这一点。

## 问题2：为什么需要两步（识别token + 递归求值）？

### 类比：做数学题

你遇到 `"5 + 4 * 3"` 时，会：

第一步：理解题目
- 识别出：数字5、加号、数字4、乘号、数字3
- 这就是"识别token"（词法分析）

第二步：计算答案
- 知道：先算 `4 * 3 = 12`，再算 `5 + 12 = 17`
- 这就是"递归求值"（语法分析+计算）

你不能直接跳到计算，必须先理解题目。

### 为什么不能直接从字符串计算？

想象你是一个"计算器机器人"，接收到字符串 `"5+4*3"`：

```python
# 错误方式：直接从字符串计算
def calculate_wrong(s):
    # 问题1：你怎么知道"5"是一个完整的数字，不是"5+"的一部分？
    # 问题2：你怎么知道"*"是乘号，不是变量名的一部分？
    # 问题3：你怎么知道运算顺序？应该先算4*3还是5+4？
    return ???  # 无法直接计算！
```

你需要先理解这个字符串的结构。

### 两步法的必要性

#### 第一步：识别token（词法分析）
把字符串变成结构化数据：

```
输入： "5 + 4 * 3"
输出： tokens = [
  {type: NUMBER, value: "5"},
  {type: PLUS},
  {type: NUMBER, value: "4"},
  {type: MULTIPLY},
  {type: NUMBER, value: "3"}
]
```

好处：
- 每个元素有明确的含义
- 空格被忽略
- 容易检查语法错误

#### 第二步：递归求值
有了token数组，才能按优先级递归计算：

```
看到 tokens = [5, +, 4, *, 3]
找到主运算符：+（因为*的优先级更高，在括号或子表达式中）
分裂：左边=[5]，右边=[4, *, 3]
递归计算右边：4 * 3 = 12
递归计算左边：5
最终：5 + 12 = 17
```

### 类比：做菜

第一步（识别token）：把食材分类
- 这是"鸡蛋"（数字5）
- 这是"加号"（运算符+）
- 这是"番茄"（数字4）

第二步（递归求值）：按食谱做菜
- 先处理优先级高的（乘法）
- 再处理优先级低的（加法）

你不能跳过分类直接做菜，必须先知道每种食材是什么。

## 总结对比

| 问题 | 简单回答 | 核心原因 |
|------|---------|---------|
| 为什么不能用eval()？ | eval()不认识`$eax`这样的符号 | 需要处理调试器特有的符号（寄存器、内存地址） |
| 为什么需要两步？ | 必须先理解再计算 | 字符串是"平面"的，需要转换成结构化数据才能计算 |
